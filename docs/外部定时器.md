# 外部定时器配置（解决 GitHub cron 不可靠问题）

## 为什么要这个

GitHub 的 `schedule` 定时任务**不可靠**：官方文档承认它是 best-effort——
高负载时会延迟甚至丢弃，**低活跃度仓库会被大幅降频**。

实测：配置 `*/10 * * * *`（每 10 分钟），实际一天只触发了 **2 次**
（11:03、18:25，间隔 7 小时）。

**解决办法**：用外部定时服务（如 cron-job.org，免费）按时调用 GitHub 的
`workflow_dispatch` API 来触发本 workflow。这样触发时机就不再依赖 GitHub。

> workflow 里已经配了 `workflow_dispatch:`，所以**不需要改任何代码**。

---

## 步骤 1：创建 GitHub Token

1. 打开 https://github.com/settings/tokens?type=beta （Fine-grained tokens）
2. 点 **Generate new token**
3. 填写：
   - **Token name**: `trigger-analyze`（随便起）
   - **Expiration**: 建议 90 天或自定义（到期需重建，见文末"维护"）
   - **Repository access**: 选 **Only select repositories** → 勾选本项目仓库
   - **Permissions** → Repository permissions → 找到 **Actions** → 设为 **Read and write**
4. 点 **Generate token**，**立刻复制**（页面关掉就再也看不到了）

⚠️ **安全提醒**：这个 token 只能触发 Actions，权限很小，但仍属敏感凭据。
不要提交到仓库、不要发给别人。如果泄露，到上面那个页面 Revoke 即可。

---

## 步骤 2：在 cron-job.org 建定时任务

1. 注册 https://cron-job.org （免费）
2. **Create cronjob**，填写：

| 字段 | 值 |
|------|-----|
| **Title** | `football-analyze` |
| **URL** | `https://api.github.com/repos/<用户名>/<仓库名>/actions/workflows/analyze.yml/dispatches` |
| **Schedule** | Every 10 minutes（或自定义 `*/10 * * * *`） |
| **Request method** | `POST` |

3. 展开 **Advanced** → **Headers**，加两条：

| Key | Value |
|-----|-------|
| `Authorization` | `Bearer <步骤1的token>` |
| `Accept` | `application/vnd.github+json` |

4. **Request body** 填：

```json
{"ref":"main"}
```

（`main` 是你的默认分支名；如果是 `master` 就改掉）

5. 保存，然后点 **TEST RUN** 测试

**成功标志**：看到 HTTP **204**（No Content）——这是 GitHub 的正常响应。
如果是 401/403，说明 token 或权限不对；如果是 404，说明仓库路径或分支名写错。

---

## 步骤 3：验证

触发成功后，去 GitHub → Actions →「赛前分析调度」，应该能看到一条
`workflow_dispatch` 触发的运行（触发者显示为你的账号）。

---

## 建议：保留 GitHub 的 cron 作为双保险

`.github/workflows/analyze.yml` 里的 `schedule:` 不用删——它虽然不可靠，
但偶尔能触发也是白赚。**外部定时器 + GitHub cron 两条路一起触发**，互相补位。

（`concurrency` 已配置为同一时间只跑一个，所以两边同时触发也不会冲突。）

---

## ⚠️ 触发间隔要和「判定窗口」匹配

`scheduler.py` 的判定窗口是 **[目标-TOLERANCE_MIN, 目标+2] 分钟**。
**窗口宽度必须 ≥ 外部定时器的触发间隔**，否则中间会被"跳过"、漏掉比赛。

当前设计：**不做内部循环**（`RUN_MINUTES = 0`），每次触发只检查一轮就退出，
触发频率完全交给外部定时器 —— 这样 runner 占用最少。

| 项目 | 值 | 说明 |
|------|:---:|------|
| cron-job.org 触发间隔 | **10 分钟** | ⚠️ 必须是 10 分钟（见下方说明）|
| 分析时点 | **T-10 / T+5** | 开赛前 10 分钟、开赛 5 分钟后（`WINDOWS`）|
| `TOLERANCE_MIN`（scheduler.py） | **8** | 窗口宽 10 分钟 = 触发间隔 ✓ |
| `RUN_MINUTES` | **0** | 单次检查，不循环 |
| `CHECK_INTERVAL` | 300 | `RUN_MINUTES=0` 时不生效 |

**为什么必须 10 分钟触发**：窗口宽度 = `TOLERANCE_MIN + 2`，必须 ≥ 触发间隔，否则会漏。
若用 15 分钟触发，容差需 ≥13，T-10 的窗口就会变成 [−3, 12]——**会跑到开赛后**，
拿到的就不是赛前盘了。10 分钟触发 + 容差 8 → 窗口 [2, 12]，**始终在开赛前** ✓

具体窗口：

| 时点 | 距开赛窗口 | 含义 |
|------|:---:|------|
| **T-10** | [2, 12] 分钟 | 开赛前 2~12 分钟 |
| **T+5** | [−13, −3] 分钟 | 开赛 3~13 分钟后（收盘盘）|

> 效果：每 10 分钟检查一次，窗口 10 分钟宽 → **每场必命中一次**，不会漏。

**改动其中任何一个，记得同步改另一个**（窗口宽度 = `TOLERANCE_MIN + 2` ≥ 触发间隔）：

| 你改成 | 也要改 |
|--------|-------|
| 触发间隔 10 → 15 分钟 | `TOLERANCE_MIN` 8 → 13（但 T-10 会跑到开赛后，不建议）|
| `TOLERANCE_MIN` 8 → 5 | 触发间隔要 ≤ 7 分钟 |

**另一种方案**（想减少触发次数）：把 `RUN_MINUTES` 设成略小于触发间隔的值（如 9），
`TOLERANCE_MIN` 可以调回 10 —— 一次运行内部覆盖一段时间，但 runner 占用会大幅上升。

---

## 维护

| 事项 | 说明 |
|------|------|
| **Token 过期** | 到期后 cron-job.org 会返回 401，重新建 token 并更新那个 Header 即可 |
| **cron-job.org 免费额度** | 免费档支持每分钟触发，足够用；它会记录每次执行的响应码，便于排查 |
| **想换服务** | 任何能发带自定义 Header 的 POST 请求的服务都行（如 EasyCron、UptimeRobot 的 HTTP 监控） |

---

## 附：命令行手动触发（测试用）

仓库里提供了 `trigger_workflow.py`，可以在本地测试 token 是否有效：

```bash
python trigger_workflow.py --repo <用户名>/<仓库名> --token <你的token>
```

成功会打印 `HTTP 204`。
